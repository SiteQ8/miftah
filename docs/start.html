Run it on your repository

Four steps to a cryptographic inventory and a gate that stays quiet until somebody adds something new.

1

Scan

No install, no configuration, no account. Nothing leaves your machine.

npx github:SiteQ8/miftah scan .

You get the inventory, the exposed window in years, and the highest risk assets in order. Add --html report.html for something to hand to somebody else, or --cbom cbom.json for a CycloneDX 1.6 inventory your SBOM tooling already understands.

2

Accept what is already there

This is the step people skip, and skipping it is why scanners get deleted. On any codebase with history the gate fails from the first run and never stops, so somebody removes it within a week.

npx github:SiteQ8/miftah baseline .
git add .miftah-baseline.json
git commit -m "Accept current cryptography"

Now the build fails only on what arrives after today. Nothing is hidden: every accepted finding still appears in the report and the CBOM, and every run tells you how many the baseline absorbed and how many have been fixed since.

The baseline is meant to be read

Each entry carries the rule, the file and the title beside its hash, so a reviewer can see what is being accepted. A baseline nobody reads is a rubber stamp. Delete an entry to start failing on it again.

Fingerprints ignore line numbers on purpose, so moving code does not invalidate the baseline. They do include the file and the key size, so the same call in a new file counts as new and RSA-1024 becoming RSA-4096 registers as a change. Run miftah baseline . --prune to drop entries whose findings are fixed.

3

Put it in the pipeline

Copy one of these. All three gate against the baseline, so they stay quiet until something new appears.

# Miftah in GitHub Actions.
#
# Copy this to .github/workflows/miftah.yml in your repository.
#
# Before the first run, record what is already there so the build fails only on
# what arrives after today:
#
#   npx github:SiteQ8/miftah baseline .
#   git add .miftah-baseline.json && git commit -m "Accept current cryptography"
#
# Without that step the job fails from the first run and never stops, and the
# usual outcome is that somebody deletes the workflow.

name: Cryptographic inventory

on:
  push:
    branches: [main]
  pull_request:
  schedule:
    # Nothing in the tree changed, but the horizon moved a week closer.
    - cron: '0 6 * * 1'

permissions:
  contents: read
  security-events: write

jobs:
  miftah:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Scan
        run: |
          npx --yes github:SiteQ8/miftah scan . \
            --baseline .miftah-baseline.json \
            --sarif miftah.sarif \
            --cbom cbom.json \
            --fail-on high

      # Uploaded even when the scan step fails, or a failing build hides the
      # very findings that caused it.
      - name: Upload to code scanning
        if: always()
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: miftah.sarif
          category: miftah

      - name: Keep the inventory
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: cbom
          path: cbom.json
# Miftah in GitLab CI.
#
# Record a baseline first, or the job fails from the first pipeline:
#
#   npx github:SiteQ8/miftah baseline .
#   git add .miftah-baseline.json && git commit -m "Accept current cryptography"

miftah:
  image: node:20-alpine
  stage: test
  script:
    - npx --yes github:SiteQ8/miftah scan .
        --baseline .miftah-baseline.json
        --sarif miftah.sarif
        --cbom cbom.json
        --fail-on high
  artifacts:
    when: always
    paths:
      - miftah.sarif
      - cbom.json
    expire_in: 30 days
#!/bin/sh
# A pre commit hook that blocks new cryptographic debt.
#
# Install with:
#   cp examples/ci/pre-commit.sh .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit
#
# It only fails on findings the baseline does not already accept, so it stays
# quiet until you add something new.

if [ ! -f .miftah-baseline.json ]; then
  echo "miftah: no baseline yet. Run: npx github:SiteQ8/miftah baseline ."
  exit 0
fi

npx --yes github:SiteQ8/miftah scan . \
  --baseline .miftah-baseline.json \
  --fail-on high \
  --quiet || {
    echo ""
    echo "miftah: this commit introduces cryptography that is broken or quantum exposed."
    echo "        Run 'npx github:SiteQ8/miftah scan . --baseline .miftah-baseline.json' to see it."
    echo "        If it is deliberate, accept it with 'miftah baseline .' and commit the baseline."
    exit 1
  }

The GitHub workflow also uploads SARIF, so findings appear in code scanning beside everything else your team already reviews. With a baseline in place, only the new ones show up there.

Exit codeMeaning
0Nothing at or above the threshold that the baseline has not accepted
1Something new at or above --fail-on
2The scan itself could not run, for example a missing baseline file
4

Set the assumptions to your situation

The defaults assume ten years of required secrecy, a five year migration and a 2033 horizon. The horizon is an assumption rather than a prediction, which is why it is a slider in the console and a flag here.

miftah scan . --shelf-life 25 --migration 7 --horizon 2035 --exposure internal
FlagWhat it means
--shelf-lifeYears the data must stay secret. Medical records and legal archives justify a long one, a session token almost none.
--migrationYears a full migration realistically takes in your organisation.
--horizonYear a capable quantum computer is assumed to exist.
--exposureinternet, partner, internal or airgapped. Lowers the score but never to zero.

When it looks wrong

It found more than a thousand findings

Almost certainly a dependency lockfile. A package-lock.json carries a sha512 integrity hash per package, which is thousands of entries that say nothing about your cryptography. Lockfiles are skipped by default; --lockfiles scans them anyway.

It flagged our own list of weak algorithms

Naming an algorithm is not using one. A denylist, a grading table, a test asserting the weak ones get caught, and a fixture named vulnerable_config.env are all tagged and downgraded rather than reported as vulnerabilities. They are downgraded and never dropped, because a real key committed to a test fixture is still a real key. --strict turns all of it off.

It flagged a placeholder

Values like your-app-password and ${API_KEY} are ignored. If a real one slips through, the fastest fix is to accept it in the baseline and open an issue with the line, since a missed placeholder pattern is worth fixing for everybody.

It reported nothing at all

Check the file count in the summary. If it read zero files, the tree may be entirely in a language or format outside the allowlist, and that is worth reporting. A scanner that reads nothing is worse than no scanner, because a clean report retires the question.

The build fails and we cannot fix it today

Accept it deliberately rather than removing the gate. Run miftah baseline ., commit the file, and the entry is visible to anybody reviewing it later. That is an honest record; a deleted workflow is not.
